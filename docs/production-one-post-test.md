# Bounded one-post federation test executable

This deployment-specific synthetic tool is separate from reusable CMS behavior. It is prepared locally; execution requires the AP owner's approved real-identity rollout configuration and scoped credentials. It never migrates or provisions anything.

`cmd/production-one-post` uses existing restricted CMS runtime roles in the isolated staging schema. Those grants are schema/table/column scoped, not per-publication RLS. A fresh test publication needs no expanded grant, while the application still scopes every request/query. It takes a namespaced publication lock and refuses prior data. It creates one draft, publishes, and immediately withdraws the same identity through the real CMS handler BEFORE network delivery begins. Two immutable obligations then pass through the normal durable mapper/worker. No history, extra post, edit, republish, media or induced failure is added.

The process is bound to the publication and HTTPS origin supplied by the reviewed real-identity rollout manifest; it has no personal domain or actor hardcoding. The earlier separate test identity/domain proposal was rejected and its artifact is superseded. The private receiver stays loopback-only. It requires explicit approval and a spend measurement less than five minutes old and below $4.50, with at least45minutes before the existing2026-10-28T03:24:10Z stop deadline. It cannot extend that budget/deadline. No public publisher or new service is involved. Additional nonsecret inputs: CONTENT_ONE_POST_APPROVED, CONTENT_ONE_POST_PUBLICATION, CONTENT_ONE_POST_ORIGIN, CONTENT_ONE_POST_ACTOR, CONTENT_TEST_SPEND_USD, CONTENT_TEST_SPEND_MEASURED_AT. Other scoped child inputs match the staging probe. Standard TLS uses the AP wrapper's child-only public CA bundle.

Success requires exactly two accepted payloads, controlled-peer Create/Delete receipt metadata matching the immutable CMS bytes and canonical object identity, exact pinned Create/Delete actor and Article attributedTo, and current public HTTPS410 Tombstone. Failure output separately records withdrawal_committed, withdrawal_accepted and withdrawal_observed, plus withdrawal_commit_state to distinguish an attempted but unconfirmed write; durable obligations/evidence are preserved. A hard stop can leave remote deletion unresolved. Never reset/replay a used publication. No writing recovery command is included in this milestone.

Unit/race tests cover start gates, fixed scope, unchanged old-loader rejection and negative peer evidence. A real PostgreSQL/Node integration test is authored for pre-delivery withdrawal, exactly two events, one-use protection and outage preservation. Its invocation was rejected by automatic approval review because the test harness creates temporary databases/roles; it did not execute and was not rerouted. Do not describe this new runner as database-verified until that test is approved and run. Earlier five-event cloud and CMS database evidence is separate.

The fresh real-identity activation handoff now supplies the actual publication/origin/actor in deployment configuration. A live READ ONLY check confirmed the fresh publication has zero CMS rows/queued events, existing exact INSERT/UPDATE-column grants are present, runtime role flags/memberships remain restricted, and checked website/auth/AP schemas are inaccessible. No new CMS credentials/grants or production mutations were performed by the Go owner. AP production installation/schema must remain separate from the CMS child installation/schema, even while they share one PostgreSQL database.
