# Owner moderation API v1

Owned entirely by the Fedify module, on its internal listener only. Authenticate with the dedicated publication-scoped Bearer `MODERATION_TOKEN`, distinct from `PUBLISHER_TOKEN`. The publisher credential is rejected by moderation routes; the moderator credential cannot publish, enroll archives, resolve receipts or read publisher status. The Go CMS framework does not host a moderation UI/client or receive this token. A separately authorized API client must keep credentials server-side and constrain requests to these routes; any browser-facing client would need its own owner authentication and CSRF/origin checks. This contract does not require a UI. Default disabled; 403 feedback_disabled until collection is explicitly enabled after migration/grants and authorization/privacy checks.

GET /internal/v2/feedback?state=pending&limit=50&cursor=0 returns {items:[...],next_cursor:string|null}. States: pending, approved, rejected, deleted. Limit1–100 (default50); cursor decimal offset0–9999999 (default0). Ordered received_at descending then id. This is a live moderation list, not a frozen export; concurrent changes can shift offset pages, so refresh after mutations. Each item has id, activity_id, actor_id, target, kind(reply|like|boost), sanitized html, state, source_updated_at and received_at. Dates are UTC ISO8601. Deleted items have empty html. Responses are no-store. Attribution is a remote actor URL; do not fetch arbitrary avatars/URLs server-side without the existing safe loader.

POST /internal/v2/feedback/moderate with Content-Type application/json and {id,decision:"approved"|"rejected",expected_activity_id}. Schema: moderate.schema.json. Use the exact activity_id from the reviewed item. A remote edit changes that ID and resets pending. 409 feedback_changed means reload and review the new body; never automatically retry approval with a new ID. 404 feedback_not_found means absent/deleted, or approval blocked by an actor block. Approval never restores deleted content. Same-revision repeat decisions are harmless.

POST /internal/v2/feedback/block with {actor,blocked:boolean}. Schema: block.schema.json. Blocking rejects existing nondeleted feedback and prevents new feedback from the actor; unblocking does not restore old approvals. This blocks blog interactions only, not the remote account's Follow relationship.

Both mutations return200 {result:"applied"}. Body limit2MiB; malformed JSON400, oversized413, content-type415, invalid fields422, missing/wrong bearer401, disabled403, service unavailable503. Do not log body/token or treat503 as success. Mutations use actor-level serialization so concurrent edits/blocks cannot silently make unreviewed content public.

Public approved collections use standard Fedify OrderedCollection routes: /ap/objects/{publication}/{id}/replies, /likes, /shares. Only first-level public replies directly targeting a local public Article are supported. Private replies are ignored; edits return to pending; signed author Delete and Undo reactions remove feedback. Collections hide everything after parent withdrawal. No automatic retransmission of comments to other followers. The website may show approved content read-only without adding public login.

Enablement: migration003_feedback.sql, FORCE RLS and exact existing runtime privileges: SELECT/INSERT/UPDATE on feedback; SELECT/INSERT on feedback_tombstones; SELECT/INSERT/DELETE on feedback_blocks. No new role/key/schema or protected-state grant. Enabled startup checks table presence, forced RLS and required grants and fails closed. Test API authorization and public-collection privacy before explicitly setting ACTIVITYPUB_FEEDBACK_ENABLED=true on API AND worker. Removing a moderation client neither disables collection nor changes stored decisions. Without an explicit authorized decision, new items stay pending and private; rejected items stay private. Preserve feedback, tombstones, blocks and the AP credential when removing CMS integration. No automatic approval, data deletion or key/token rotation follows from a client removal.
